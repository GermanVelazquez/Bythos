## Exploration: Bythos móvil + QR (recibir archivos/links del celular por WiFi local, TLS)

### Current State

Bythos desktop (`bythos-desktop` Go module) is a single `.exe` with an embedded React UI, serving everything on `http://localhost:8080` only. `desktop/main.go` wires: SQLite (`db.Abrir`), embedded UI (`fs.Sub` over `go:embed all:ui/dist`), the HTTP server (`api.Servidor.Rutas()`), and the native window (`ventana.Abrir`). There is exactly one `http.ListenAndServe("localhost:8080", ...)` call — no LAN listener exists today.

`api/server.go`'s `Rutas()` registers all HTTP routes and wraps everything in `conGuardia`, a Host+Origin allowlist (not open CORS): only `localhost:8080`/`127.0.0.1:8080` Host, and Origin either the embedded UI (`http://localhost:8080`), Chrome-extension prefix, or (`BYTHOS_DEV=1`) Vite `:5173`. This guard is meant for browser-borne requests (CSRF/DNS-rebinding); it is Origin/Host-based, not identity-based, and is the wrong model to reuse for a phone (no Origin header from a native TLS client, and no concept of per-device trust).

`api/agente.go` (`POST /api/agente/terminal`) shows the codebase's existing pattern for a *more dangerous* route needing stricter treatment than `conGuardia`: exact-Origin check (no prefix), a package-level mutex + timestamp for a crude rate window (`ventanaAgente = 3s`), and injectable seams (`var lanzadorAgente`, `var prepararWorkspaceAgente`, `var exeActual`) so tests never hit the real OS. This is the template to imitate for pairing/upload endpoints, but the LAN listener needs a genuinely different trust model: real per-device tokens, not Origin string matching (a phone client is not a browser and controls its own headers).

`api/origen.go` + `db/eventos.go` implement the Historial: `X-Bythos-Origen` (`app`/`extension`/`agente`, else `desconocido`) + free-text `X-Bythos-Actor` (≤80 chars) get attached to every mutation via `s.registrarEvento(...)`, which never fails the request (log-only on write error). Origins are a closed Go `const` set (`OrigenApp`, `OrigenExtension`, `OrigenAgente`, `OrigenDesconocido`) validated both in `api/origen.go` and redundantly in `db.normalizarOrigen` ("DB is the last line of defense"). Adding `celular` means touching both validators plus `AccionArchivoSubido`-style constants if a device-specific action is wanted (or reusing existing `AccionArchivoSubido`/`AccionRecursoGuardado` with `origen=celular` and `actor=<device name>` — the existing schema already has an actor field, no schema change needed for basic device labeling).

**Paso 0 (uncommitted, treated as baseline per instructions):**
- `desktop/archivos/archivos.go`: content-addressed disk store (`Base()/<sha2>/<sha256>.<ext>`), streaming save via `io.Copy` to a temp file with `io.MultiWriter(tmp, hasher)` (never buffers whole file in memory), atomic same-volume rename, dedupe on existing hash, magic-byte-only type detection (`detectarTipo`) with an explicit whitelist (PDF/MP4/MOV/WebM/MKV/PNG/JPEG/GIF/WEBP/DOCX/XLSX/PPTX-without-macros/TXT/MD), hard rejection of anything that looks like HTML/SVG/markup even if valid UTF-8. `TamanoMaximo = 2 GiB` is a `var` (test-overridable), enforced via `http.MaxBytesReader` in the HTTP handler *before* `archivos.Guardar` is called — this cap enforcement point matters for a chunked mobile upload protocol, since a resumable transfer can't rely on a single `MaxBytesReader` around one request body.
- `desktop/db/archivos.go`: `archivos` table, atomic `INSERT ... ON CONFLICT(sha256) DO NOTHING RETURNING` dedupe (documented fix for a real TOCTOU bug from a prior SELECT-then-INSERT version — instructive precedent for any new concurrent-write path the phone feature adds).
- `desktop/api/archivos.go`: `POST /api/archivos` streams multipart directly via `r.MultipartReader()` (never `ParseMultipartForm`), one **single request, single body** upload — no chunking/resume support exists yet. `GET /api/archivos/{id}/contenido` serves with Range support (`http.ServeContent`), MIME-locked headers (`X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox; default-src 'none'; frame-ancestors 'self'` except a documented PDF exception without `sandbox` due to two cited Chromium bugs) and a `Sec-Fetch-Site` check as a supplementary defense against being embedded from cross-origin pages (since `<img>/<video src>` loads don't send `Origin`).

`desktop/db/db.go` is the sole owner of SQL: `Abrir()` runs `sql.Open` → `Ping` → `PRAGMA foreign_keys/journal_mode=WAL` → `crearTablas()`, and `crearTablas` is the single serialized migration entrypoint: base `CREATE TABLE IF NOT EXISTS` blocks (folders/resources/agenda/import_lotes) followed by ordered migration functions (`migrarProgreso`, `migrarImportLotes`, `crearTablaArchivos`, `migrarArchivoID`, `crearTablaEventos`) each idempotent via `PRAGMA table_info` column checks before `ALTER TABLE`. Any new "paired devices" / "pairing codes" table follows this exact idempotent pattern — one new `crearTabla*` function called from `crearTablas`, in dependency order (a `dispositivos`/`pares` table with a hashed-token column would slot in right after `crearTablaArchivos`/before `crearTablaEventos`, since events may reference device rows only loosely via `actor` text, not a foreign key).

`desktop/db/db.go`'s `CarpetaDatos()` resolves `%APPDATA%\Bythos` (never next to the `.exe`, since Program Files blocks writes) — this is also where a generated TLS keypair/cert and a device-token store would naturally live, next to `bythos.db` and the `archivos/` blob store.

`installer/bythos.iss`: per-user install (`PrivilegesRequired=lowest`, `DefaultDirName={localappdata}\Bythos`), no admin rights requested or required for install. This is orthogonal to (and does NOT resolve) the Windows Firewall prompt question for the LAN listener — see Risks.

`desktop/ui/src/App.jsx` (2215+ lines) has a sidebar nav array around line 169 (`{ id: 'historial', label: 'Historial', icon: 'clock' }` and siblings) driving view switching (`view === 'historial'` checks later in the file) — this is the exact insertion point for a new `{ id: 'recibir', label: 'Recibir del celular', icon: '...' }` nav entry and its `view === 'recibir'` render branch. `desktop/ui/src/Archivos.jsx` shows the established UI pattern for this feature area: a self-contained modal component (`AddFileModal`) that takes `onUpload(file, carpetaId, setProgreso)` as a prop and reports progress via a callback — App.jsx must own the actual upload call (progress-reporting upload logic was not found inside `api.js`, which currently has zero raw multipart/XHR-with-progress code — `api.js` is fetch+JSON only, so file upload progress reporting is handled ad hoc where `onUpload` is implemented, likely directly in `App.jsx`). A "Recibir del celular" screen (QR + pending-device approval + live transfer list) is a new, larger, stateful screen than the existing modals and will need its own component file (`ReceptorMovil.jsx` or similar), mirroring the `Archivos.jsx` separation-of-concerns choice ("App.jsx ya es grande, componentes separados a propósito").

No mobile app, QR generation, TLS listener, pairing, or device-token code exists anywhere in the repo today. `docs/DESARROLLO.md`'s roadmap explicitly lists Paso 0 as "base para la futura app móvil" — this change is the anticipated next step, not a surprise addition.

### Affected Areas

- `desktop/main.go` — must start (or lazily start/stop) a second listener; current file is intentionally ≤60 lines ("director, no piensa"), so listener lifecycle logic should live in a new package (e.g. `desktop/lan/`), not inline here.
- `desktop/api/server.go` — `conGuardia`'s Host/Origin model does not fit a native TLS client; the LAN listener needs its own `http.Handler`/mux with device-token auth, not `conGuardia`.
- `desktop/api/agente.go` — closest existing precedent for a "more dangerous than default" route: exact-Origin check, rate-limit-by-mutex pattern, and DI seams for testability. Worth imitating structurally, not reusing directly.
- `desktop/api/origen.go` + `desktop/db/eventos.go` — need a new `celular`/`OrigenCelular` origin constant in both the Go-side allowlist and the DB-side `normalizarOrigen`; existing `actor` field already covers "device name" without a schema change.
- `desktop/db/db.go` — needs one new idempotent `crearTabla*` (paired devices: hashed token, device name, first-seen, revoked flag) inserted into `crearTablas()` in the same ordered-migration style.
- `desktop/archivos/*`, `desktop/db/archivos.go`, `desktop/api/archivos.go` — the file-landing path to reuse as-is for the final "commit" step of an upload; the single-request multipart handler is NOT reusable unmodified for chunked/resumable large-video uploads (needs a new assembly-then-handoff-to-archivos.Guardar path, or a change to accept an already-hashed-on-device-verified stream).
- `desktop/api/metadata.go` — the SSRF-guarded fetch client (`clientSeguro`/`dialerSeguro`/`ipBloqueada`) is exactly the code path a "save link from phone" route should reuse for metadata enrichment; do not build a second metadata fetcher.
- `desktop/ui/src/App.jsx` (sidebar array ~line 169, `view` switch) and `desktop/ui/src/Archivos.jsx` (modal/progress-callback pattern) — new "Recibir del celular" screen needs a new component file plus one new sidebar entry.
- `installer/bythos.iss` — non-admin per-user install; does not address Windows Firewall consent for the new listener (separate risk, see below); may eventually need a bundled/documented firewall-rule story.
- New, currently-nonexistent: `desktop/lan/` (or similar) Go package for the TLS listener + pairing + cert generation; `mobile/android/` (or a separate repo) for the Kotlin app.

### Approaches

1. **Same-binary second listener (`http.ListenAndServeTLS` on a LAN-bound address, separate `http.ServeMux`), started only while "Recibir del celular" screen is open** — description: `main.go` starts port :8080 as today; the LAN listener is started/stopped by the UI screen's lifecycle (open → listen, close/app-exit → stop), living in a new `desktop/lan` package with its own mux, own auth middleware (device-token, not `conGuardia`), and calling into the *existing* `db`/`archivos` packages for persistence.
   - Pros: reuses all Paso 0 file-landing logic and the eventos/origen pattern verbatim; minimal blast radius; listener-off-by-default limits attack surface to exactly when the user chose to receive; fits the existing "one process, one .exe" philosophy (no second service to install/manage).
   - Cons: cert/pairing state must be Bythos-app-lifetime, not request-lifetime, forcing new package-level state alongside `main.go`'s existing globals; still shares the Go process (a crash/blocking bug in the LAN handler risks the whole app, though this is already true of the existing single-process model).
   - Effort: Medium.

2. **Separate always-on background listener started at app launch, gated by a runtime "reception enabled" flag instead of screen-open/close** — description: same package, but the socket binds at `main.go` startup regardless of whether the user ever opens the screen, and requests are simply 403'd/dropped when reception is toggled off.
   - Pros: avoids bind/unbind races when the user opens/closes the screen quickly; QR can be pre-generated.
   - Cons: directly contradicts the confirmed decision ("only open while the user enables reception / the screen is open") — a bound-but-gated socket is still a live attack surface and a Windows Firewall prompt trigger at every app launch, which is worse UX and worse security posture than the decided approach.
   - Effort: Medium (rejected — violates a stated decision, listed only for completeness).

3. **Separate sidecar process/service for the LAN listener (spawned by `bythos.exe`, IPC to the main process for DB/file access)** — description: split the LAN-facing surface into its own OS process so a crash or a future vulnerability there can't directly corrupt the single `*sql.DB` connection or touch the main window process.
   - Pros: stronger isolation; a hostile phone payload hitting a bug in the new code can't crash the whole desktop app.
   - Cons: needs IPC (named pipe or a second localhost port) duplicating almost everything `db`/`archivos` already do safely with `SetMaxOpenConns(1)`; against Bythos's explicit "one file, minimal moving parts" design; installer/process-management complexity (spawning/watching a child process on Windows) is a new failure class the project has avoided everywhere else.
   - Effort: High.

**Recommendation**: Approach 1 (same-binary second listener, screen-lifecycle-bound). It is the only option that matches the explicit design decision, reuses every already-hardened piece of Paso 0 and the eventos/origen model without adapters, and keeps Bythos's core identity ("un solo .exe, mínimas dependencias") intact. Approach 3's isolation benefit is real but disproportionate for a hobby-scale local app with no untrusted multi-tenant exposure; Approach 2 is directly excluded by a confirmed decision.

### Risks

- **Windows Firewall consent for a non-admin listener is NOT guaranteed passable by every user.** Verified via search: Microsoft's own guidance states a *genuine* standard user (not a member of the local Administrators group) needs administrator credentials to approve a firewall exception — they cannot self-approve "Allow access." In practice most single-PC home users ARE local admins running under UAC Admin Approval Mode, where the firewall consent becomes a simple Yes/No elevation prompt they can self-approve without a password — but this is NOT universal (managed/corporate/shared-family PCs, a parent/child non-admin account, school-issued laptops). Bythos's installer is deliberately non-admin (`PrivilegesRequired=lowest`), so it will very plausibly be installed and used by a Windows account that is itself a true standard user, where the LAN feature could silently fail to be reachable (blocked at the firewall) with no application-level way to detect or fix it. **Needs a spike**: reproduce on a real non-admin Windows account, confirm the prompt behavior first-hand (not just via search), and design a clear in-app diagnostic ("no se pudo confirmar acceso desde la red" / firewall guidance) for when the LAN port never becomes reachable rather than silently degrading.
- **Future Android "Local Network Permission" (ACCESS_LOCAL_NETWORK)**: verified via Android Developers docs — Android is introducing a runtime permission (opt-in at Android 16, **mandatory enforcement at Android 17 for apps targeting SDK 37+**) gating ALL outgoing LAN traffic (TCP connect, UDP) regardless of discovery mechanism (mDNS or not) — a plain HTTPS connection to a QR-provided IP:port WILL require this permission on future OS versions. Not an immediate blocker (current Android versions don't enforce it, and the app can target a lower SDK for a while), but the Kotlin app's manifest/permission-request flow should be designed with this in mind from day one so the later SDK bump isn't a rewrite.
- **NEARBY_WIFI_DEVICES / ACCESS_FINE_LOCATION**: NOT required for this design specifically, because the QR already supplies IP+port (no on-device Wi-Fi scanning/discovery is needed) — confirms the "folder chosen on phone, IP from QR" design avoids the heavier location-adjacent permission entirely; only relevant if a future version adds LAN auto-discovery (mDNS/SSDP) instead of QR-only.
- **Self-signed cert + pinning is real security but has real failure modes**: cert rotation (what happens to already-paired phones when the PC regenerates its cert — e.g., after `%APPDATA%\Bythos` is cleared, reinstalled, or the private key is deliberately rotated) needs an explicit re-pairing story, or paired phones silently fail with a TLS pinning error that looks like "no connection" to the user.
- **First-connection PC-side approval UX**: "¿Permitir este celular?" needs a decision for what happens to in-flight pairing attempts if the desktop app is closed/backgrounded when the phone connects (queued? rejected? — the screen-open-gated listener design means the phone literally cannot reach the PC unless the screen is open, which actually simplifies this: no background approval queue needed, consistent with approach 1).
- **Chunked/resumable upload correctness**: the existing `archivos.Guardar` design assumes a single contiguous `io.Reader` hashed in one pass; a resumable protocol needs either (a) chunks reassembled into one file before a single `archivos.Guardar` call (simplest, reuses existing code untouched, but needs temp-chunk storage + integrity check design), or (b) a new streaming API in `archivos` that accepts out-of-order/resumed writes (more invasive, higher risk of introducing a first vulnerability into an otherwise very carefully hardened package). Recommend (a) for v1.
- **2 GiB cap enforcement across chunks**: `archivos.TamanoMaximo` is currently enforced via one `http.MaxBytesReader` per single-request body; a chunked protocol must re-derive this cap by tracking cumulative bytes received across chunks server-side (can't trust the phone's declared total size).
- **Android share-intent variety**: `ACTION_SEND`/`ACTION_SEND_MULTIPLE` cover link/PDF/image/video/doc sharing generically via `content://` URIs, but large-video streaming from a `content://` URI (no direct filesystem path, must go through `ContentResolver.openInputStream`) combined with a foreground service/WorkManager for long uploads is real Android complexity that deserves its own spike before committing to an upload architecture.
- **QR payload size**: LAN IP + port + SHA-256 fingerprint (64 hex chars) + one-time pairing code all in one QR is a non-trivial amount of data; needs an early check that a reasonably-sized QR (scannable at typical phone-to-monitor distance) can hold all of it, or the fingerprint should be verified out-of-band differently (e.g., truncated hash + code, if full SHA-256 makes the QR too dense).
- **Multiple network interfaces (VPN, Hyper-V vSwitch, hotspot)**: binding to `0.0.0.0` and reporting "the" LAN IP requires picking the right interface among possibly several active ones (VPN adapters, Hyper-V/WSL virtual switches, a phone-tethered hotspot) — naive "first non-loopback IPv4" logic is likely wrong on developer/gamer/VPN-using machines; needs explicit interface-selection logic and probably a manual override in the UI if auto-detection guesses wrong.
- **Skill registry has no Android/Kotlin/Go-networking-specific skill** — no existing project skill matched this topic; propose/design phases should not expect skill-injected guidance for the mobile side.

### Ready for Proposal

Yes — the desktop-side design has a clear recommended approach (same-binary, screen-lifecycle-bound second listener reusing Paso 0 and the eventos/origen model) and the mobile-side unknowns are enumerated as concrete spikes rather than open-ended uncertainty. The orchestrator should surface to the user, before `sdd-propose`, that: (1) the Windows Firewall consent risk for genuinely non-admin accounts needs a real-device spike, not just this desk research, and (2) the chunked-upload design choice (reassemble-then-Guardar vs. new streaming API) should be confirmed as reassemble-then-Guardar for v1 unless the user has a strong reason to want true streaming assembly.
